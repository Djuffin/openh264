# Duplicate census allowlist — consumed by rust/tools/census.sh (plan §7.2, Phase 5
# session A). Every line is a duplicate that is *allowed to exist*, with the class it
# was put in and the reason. Anything the instruments report that is not listed here
# fails the gate.
#
# Classes, per the Phase 5 brief's Face 1:
#   (a) cross-codec namesake matching C++ — the two codecs really do declare a type of
#       this name, so there is nothing to unify. No renames (P14).
#   (b) within-codec duplicate declaration of one entity — must be unified. Anything
#       still listed under (b) carries the phase step that owns it.
#   (c) value-divergent constant/table — each consumer reads its own values today and a
#       naive merge changes output (S6). The divergence is recorded, not repaired.
#   (d) legitimately same-named functions / opaque-boundary casts.
#
# Key is `<kind> <name> x<count>`; the count is part of the key on purpose, so a *new*
# copy of an already-allowed name fails the gate. File:line is not part of the key —
# it moves with every edit.

# Duplicate function *bodies* under one name (`find_stub_bodies.py --dups`). A ratchet,
# not a list: the instrument was blind to `src/decoder` until Phase 5 session A widened
# it, and the count went 51 -> 198 (156 of them decoder-touching). Most are the port's
# per-module transliteration of C++ header macros (`WELS_CLIP3` x9, `IS_INTRA` x8,
# `WelsClip1` x8, `ST32`/`LD32`, ...) or `decoder_core.rs` forwarding wrappers. F22 is
# the one that turned out to be a real divergence. Phases 5 and 6 drive this down;
# it may not rise.
#
# **198 -> 195 at T5.M4**, the first decrease since the instrument was widened, and it
# is F22's unification: eight names had two copies each, and the three whose bodies had
# stayed *identical* (`PredMv`, `PredInter16x8Mv`, `PredInter8x16Mv`) are the three this
# instrument could see. The other five had **diverged** — which is exactly why a
# duplicate-body count is a floor on the problem and never a measure of it.
